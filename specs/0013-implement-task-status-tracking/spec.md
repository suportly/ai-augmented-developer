<!-- section: Problem -->
## Problem

After `implement` ships a task — implementer green, spec review approved, code-quality review approved, commit landed — the task's `**Status:** pending` line in `specs/<NNNN-slug>/tasks.md` is rarely flipped to `done`. Issue #33 documents four shipped specs in a consumer project where 0/41 tasks are marked done despite all PRs being merged. The artefact that is supposed to be the canonical execution log becomes a misleading historical record, and the pipeline cannot be safely resumed after a crash because there is no on-disk signal of which tasks already ran.

The current `implement` skill says "Mark the task complete in `tasks.md`" inside step 5 of the loop ([skills/implement/SKILL.md:54](../../skills/implement/SKILL.md#L54)) but does not specify *how*, does not surface the action in the implementer or reviewer prompts, and provides no idempotency guard. In practice the step is skipped.

<!-- section: Users and stakeholders -->
## Users and stakeholders

- **Framework users running `/aiadev:implement`** — get a `tasks.md` that accurately reflects shipped work, can resume an interrupted run safely.
- **Reviewers reading shipped PRs** — can confirm at a glance which tasks were exercised by the diff without cross-referencing commits.
- **Future automation (analyze, autodev)** — can rely on `Status: done` as a load-bearing signal instead of guessing from git history.
- **Framework maintainers** — sign off on changes to `skills/implement/SKILL.md` and the `aia:` mirror.

<!-- section: Success criteria -->
## Success criteria

- After `/aiadev:implement` completes on a fresh feature, every `### TNNN` block in `specs/<branch>/tasks.md` shows `**Status:** done`. (Measurable: zero occurrences of `**Status:** pending` or `**Status:** in_progress` under task headers when the skill reports completion.)
- Re-invoking `/aiadev:implement` on a feature where some tasks are already `done` skips those tasks rather than re-executing the implementer subagent for them.
- The `tasks.md` mutation lands in the same commit as the task's code change — no extra "marker-only" commits appear in `git log`.
- The contract appears explicitly in `skills/implement/SKILL.md` (the single tracked source of truth — downstream copies are gitignored derivatives). A CI-run pytest assertion guards the loop section against accidentally stripping the status-flip wording.
- The `analyze` skill, run on a fully-shipped feature, finds zero drift between `tasks.md` status lines and merged commits.

<!-- section: Non-goals -->
## Non-goals

- Switching the task-marker syntax from `**Status:** pending` to GitHub-style checkboxes (`- [ ] T001 …`). Issue #33 lists this as optional; defer to a separate spec.
- Introducing a new `in_progress` lifecycle state between dispatch and merge. Out of scope; the recovery story is covered by the resume guard alone.
- Retroactively rewriting historical specs (`specs/0005-*` … `specs/0008-*` etc.) in consumer projects. The bulk-`sed` workaround in issue #33 is sufficient and is consumer-side, not framework-side.
- Changing the commit-granularity rule (`one task = one commit`). The status mutation rides inside the task commit, it does not get its own commit.
- Adding telemetry or progress events for external observers. Out of scope for this spec.

<!-- section: User stories -->
## User stories

### Story 1 — Status flips to done as each task ships (P1)

As a framework user running `/aiadev:implement` on an approved plan, I want each task's `**Status:**` line in `tasks.md` to be rewritten from `pending` to `done` at the moment the task's commit lands, so that the spec directory is a faithful record of what shipped and I can stop reconciling `tasks.md` against `git log` by hand.

**Acceptance scenarios** (Given / When / Then, ≥ 3 per story):

1. Given a feature with three pending tasks (T001, T002, T003) and an approved `plan.md`, when `/aiadev:implement` finishes successfully, then `tasks.md` shows `**Status:** done` under all three task headers and no other status value remains.
2. Given the implement loop has just finished T002 (implementer DONE, spec review APPROVED, code-quality review APPROVED), when the per-task commit is created, then the same commit's diff includes the `**Status:** pending` → `**Status:** done` change for T002 and only that task's status line is touched.
3. Given a feature where T001 already shows `**Status:** done` from a previous run, when `/aiadev:implement` is invoked again, then T001 is skipped (no implementer subagent dispatched) and the run starts at T002.
4. Given a per-task code-quality review returns `ISSUES`, when the loop pauses to fix and re-dispatch, then T's status remains `pending` until the eventual successful commit lands — no premature `done` mark.

### Story 2 — Pipeline recovers cleanly after a crash mid-feature (P2)

As a framework user whose `/aiadev:implement` run was interrupted (crash, network drop, manual abort) after T001 and T002 shipped but before T003 started, I want to re-run the same command and have it pick up exactly at T003 by reading the on-disk status, so that I do not redo finished work or have to manually edit `tasks.md`.

**Acceptance scenarios:**

1. Given T001 and T002 are committed and marked `done` and T003 is `pending`, when `/aiadev:implement` runs, then it announces it is resuming at T003 and dispatches no subagent for T001 or T002.
2. Given a `tasks.md` where T001 is `done`, T002 is `pending`, and T003 is `done`, when `/aiadev:implement` runs, then the skill halts with a non-zero exit before dispatching any subagent and prints a single error line of the form `ERROR: tasks.md inconsistency — T003 is done but T002 is pending. Fix tasks.md manually before resuming.` (out-of-order completion is never silently absorbed).
3. Given every task is already `done`, when `/aiadev:implement` runs, then the skill does not dispatch any implementer or reviewer subagent and instead hands off directly to the post-loop step (final review / `requesting-code-review`).
4. Given a task is found in `**Status:** in_progress` at iteration start (e.g. a crash mid-iteration before the commit landed), when `/aiadev:implement` runs, then the skill treats the task as `pending` (a started-but-uncommitted iteration left no on-disk code change worth preserving) and re-dispatches it from scratch rather than skipping it.

### Story 3 — Skill contract states the rule plainly (P2)

As a framework maintainer reading `skills/implement/SKILL.md`, I want a single, explicit step in the loop that names the file edit, the exact string transform, the timing relative to the commit, and the idempotency guard, so that the rule is enforceable and reviewable instead of relying on a half-sentence ("Mark the task complete in `tasks.md`") that has demonstrably been ignored.

**Acceptance scenarios:**

1. Given the published `skills/implement/SKILL.md`, when a reader scans the loop section, then they see a numbered step that specifies (a) which file is edited, (b) the exact transform — `**Status:** pending` → `**Status:** done` on the `### TNNN` block — and (c) that the edit is staged together with the task's code change in the same commit.
2. Given the per-task dispatch contract is now consolidated inside `skills/implement/SKILL.md` (the prior `subagent-driven-development` skill was merged in and no longer exists on disk), when the per-task workflow is described, then the status-mutation step appears once in the loop section so a maintainer reading the skill does not miss it. (Downstream copies in `.claude/skills/` and `src/aiadev/_assets/skills/` are gitignored, regenerated by `aiadev sync` and `scripts/sync_assets.py` respectively from the single source — there is no second tracked copy to enforce alignment against.)
3. Given a change to `skills/implement/SKILL.md`'s loop section, when CI runs `pytest`, then `tests/test_implement_skill_drift.py` asserts the loop section still contains the literal status-flip phrases (file-path naming, `**Status:** pending` → `**Status:** done`, the `git restore --staged tasks.md && git checkout -- tasks.md` rollback, and the word `orchestrator`); a future edit that strips any of those phrases fails the build.

<!-- section: Clarifications -->
## Clarifications

- **Resolved (cl-1):** the **orchestrator** (the `implement` skill running in the main context) performs the `**Status:** pending` → `**Status:** done` Edit on `tasks.md`, immediately before the per-task `git commit`. The implementer subagent's "Files to create or modify" list never includes `tasks.md`, so the subagent prompt stays focused on code + tests. This also gives the resume guard a single owner: the same orchestrator that reads `tasks.md` at iteration start writes the `done` marker at iteration end.
- **Resolved (cl-2):** when iteration start finds a `### TNNN` block whose `**Status:**` line is missing, malformed, or holds a value outside the allowed taxonomy (`pending | in_progress | blocked | done`), the orchestrator **halts with a non-zero exit** before dispatching any subagent and prints a single error line of the form `ERROR: tasks.md malformed at T<NNN> (line <N>): missing or unparseable **Status:** line. Fix manually before resuming.`. No auto-repair — silent recovery is exactly the failure mode this spec exists to eliminate.
- **Resolved (cl-3):** the out-of-order detection from Story 2 scenario 2 stays in scope of this spec. The resume guard's correctness invariant is **"the set of `done` task ids forms a contiguous prefix of the declared task order"**; on violation the orchestrator halts with the non-zero-exit error message defined in Story 2 scenario 2. Splitting this off into a separate "tasks.md integrity validator" spec would leave the resume guard with an implicit (and unsafe) default — the prefix check is the minimum invariant that makes safe resume possible.

<!-- section: Data touched -->
## Data touched

- **`specs/<NNNN-slug>/tasks.md` — `**Status:**` line under every `### TNNN` block.** Allowed values today: `pending | in_progress | blocked | done`. This spec only writes `done`; it does not introduce new values.
- **No database, no API, no external store.** All mutations are local file edits inside the feature's spec directory.
- **No new fields, no schema migrations.** The `tasks.md` shape is unchanged; only the values written are.

<!-- section: Out-of-band effects -->
## Out-of-band effects

- None beyond the existing per-task `git commit` (which already happens). The `tasks.md` mutation rides inside that same commit.
- No notifications sent, no third-party APIs called, no external storage written.

<!-- section: Open risks -->
## Open risks

- **Subagent-vs-orchestrator boundary** (see cl-1) — if the per-task subagent owns the Edit, a malformed subagent can ship code without the marker, regressing to today's behaviour. If the orchestrator owns it, an orchestrator bug can leave a green commit without a marker.
- **Bundled-assets template** — `src/aiadev/_assets/templates/tasks-template.md` is gitignored and regenerated by `scripts/sync_assets.py` before build, so the source-of-truth at the repo root is what consumers eventually receive; the only risk is forgetting to run `sync_assets.py` before publishing a wheel, which is already CI's responsibility.
- **Existing in-flight features in consumer projects** — features that are partly shipped under the *old* (silent) skill have inconsistent `tasks.md` files; the resume guard's strict-consistency check (Story 2 scenario 2) will surface those as errors rather than silently moving on. This is the intended behaviour but should be communicated in the changelog.
- **Verification gap on agent adherence.** The repository has no end-to-end harness that runs `implement` (the `implement` flow is agent-driven prose, not Python code), so the commit-shape acceptance scenarios (Story 1 sc1, sc2, sc4) cannot be asserted by CI. Enforcement decomposes into: (a) `aiadev.tasks_status` unit tests cover the parse/validate/mark_done logic; (b) the drift validator pins the two skill copies; (c) the skill prose itself names the exact transform, ordering, and rollback. An agent that ignores the prose can still ship a green commit without a marker — that risk is intrinsic to all skill-prose contracts in this framework and is not unique to this feature.
